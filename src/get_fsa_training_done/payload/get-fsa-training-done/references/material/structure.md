# Document structure

What each kind of teaching material is shaped like, and every rule
`FSA material verify` applies. Both come from the same definitions the checker
executes, so nothing here is a constraint the tool does not enforce.

Material is **HTML on the FSA theme**: one file per artifact, the source of
truth, from which `FSA material export` derives the `.pptx` and `.pdf`. In order
of how much a trainee learns from them: the slide deck, the lecture note, then
the lab guide. The slide layouts are in
`references/material/layouts.md`.

Universal, whatever the kind:

- `<meta charset="utf-8">`, a `<title>`, and `<meta name="fsa:kind">` naming the
  kind the filename claims, plus the kind's other required `fsa:` metas.
- `<link rel="stylesheet" href="_theme/fsa.css">` and **no styling of the page's
  own**: no `style` attribute, no `<style>`, no `<font>`. Run
  `FSA material init --dir <folder>` once to put the theme there.
- Every code block is `<pre><code class="language-…">`; a diagram is
  `<figure><pre class="mermaid">…</pre></figure>`, with an `<img>` of it beside
  the source when the document will be exported.
- Relative links and images resolve, and so do `#ids`.
- English, unless the filename ends `_vn` to mark a translation.

## Naming

| Kind | Filename |
|---|---|
| Slide deck | `^(\d{2})([a-z]?)_[A-Za-z0-9_&+-]+?(?:_vn)?\.deck\.html$` |
| Lecture note | `^([a-z0-9]+)_lecture_note(?:_vn)?\.html$` |
| Lab guide | `^[a-z0-9]+_lab_(\d{2})(?:_vn)?\.html$` |
| Lab worksheet | `^[a-z0-9]+_lab_\d{2}_worksheet(?:_vn)?\.html$` |

A lesson's deck carries its index: `01_Relational_Modelling.deck.html`. A trailing letter marks an aside outside the syllabus (`02b_...`). The lecture note is one file per module, named for its subject like the labs: `dbf_lecture_note.html` — the handbook and the appendix older modules had are parts of it. `_vn` before the extension marks a translation.


## Slide deck

What a session is taught from, on the FSA template. One `<section class="slide" data-layout="...">` per slide, slots marked `data-slot`, speaker notes in `<aside class="notes">`. The layouts and their slots are in `references/material/layouts.md`.

`<body class="fsa-deck">`. Required metas: `fsa:kind`, `fsa:module`, `fsa:objectives`, `fsa:minutes`.


## Lecture note

The module in one file: the first page a trainee opens, and what they keep as a reference and revise from before a theory exam or a job interview. It opens on how to work through the module, condenses the theory into one `topic` part per lesson in the order of the decks, and closes on review questions and the syllabus map. Handed out as the HTML and its `.pdf`, never as a `.pptx`.

`<body class="fsa-doc">`. Required metas: `fsa:kind`, `fsa:module`, `fsa:objectives`.

Each part is a `<section data-part="…" id="…">` opening with an `<h2>`, in this order. The theme numbers the headings.

| `data-part` | Heading | Required | Holds |
|---|---|---|---|
| `objectives` | Objectives | yes | Opens `After this module, learners can:`, then a list whose items each carry `data-objective` — every objective the module serves. |
| `module-map` | Module Map | yes | A table, one row per lesson in order: its title, then a link to its deck, its topic below (`#id`) and its lab where they exist. |
| `how-to-study` | How to Study This Module | yes | The routine per lesson, and how to revise from this note before the theory exam or an interview. |
| `environment` | Environment Setup | optional | What to install, pinned to versions, and how to check it works. |
| `running-domain` | The Running Example | optional | The one domain every lesson's examples share. |
| `topic` | <the lesson> | yes, repeated | One per lesson, in deck order: the theory condensed — definitions, the rules and why they hold, a minimal example, a comparison table where two things are easily confused. `<h3>` per point; prose before any example. |
| `misconceptions` | Common Misconceptions | optional | One `<h3>` per wrong belief or easily confused pair, then what is true. |
| `summary` | Summary | yes | One item per objective, carrying `data-objective`: the page to reread the night before an exam. |
| `review-questions` | Review Questions | yes | An `<ol>` of the questions a theory exam or an interviewer asks; each carries `data-objective` and a model answer in `<details>`. |
| `glossary` | Glossary | optional | A `<dl>` of the module's terms. |
| `syllabus-map` | Full Syllabus Map | optional | Derived by `derive syllabus-map`, never typed: each syllabus outline item and a link to the topic covering it. |
| `further-reading` | Further Reading | yes | Primary sources, linked. |


## Lab guide

Guided practice: shorter than an assignment, step-numbered, and checkable by the trainee without a marker.

`<body class="fsa-doc">`. Required metas: `fsa:kind`, `fsa:module`, `fsa:objectives`, `fsa:minutes`.

Each part is a `<section data-part="…" id="…">` opening with an `<h2>`, in this order. The theme numbers the headings.

| `data-part` | Heading | Required | Holds |
|---|---|---|---|
| `objectives` | Objectives | yes | Opens `After this lab, learners can:`; items carry `data-objective`. |
| `before-you-start` | Before You Start | optional | What must already work; any starter project or worksheet. |
| `steps` | Steps | yes | An `<ol>`; each step ends in a `class="expected"` element saying what the trainee should see, with an optional `<details class="hint">`. |
| `acceptance` | Acceptance | yes | A `<ul class="checklist">` of outcomes the trainee can observe. |
| `stretch` | Stretch | optional | An extension for whoever finishes early. |


## Lab worksheet

The blank form each group fills in during a group lab: a heading and a drawn table per output. No parts are prescribed.

`<body class="fsa-doc">`. Required metas: `fsa:kind`, `fsa:module`.

## Rules — one document

Applied to every file `verify` reads.

|---|---|---|
| `MAT-D01` | error | The filename follows the module's naming convention |
| `MAT-D02` | error | Indexes are unique within a folder |
| `MAT-D06` | error | The first section states what a learner will be able to do |
| `MAT-D08` | error | A lecture note ends with review questions and somewhere to go next |
| `MAT-D09` | warning | The review questions are enough for the module |
| `MAT-D10` | error | Every code block declares a language |
| `MAT-D11` | warning | Code languages come from the known set |
| `MAT-D12` | error | Relative links resolve to a file that exists |
| `MAT-D13` | error | Link anchors resolve to an id in the target |
| `MAT-D16` | warning | The text is in the language the document declares |
| `MAT-D17` | error | A lab guide has ordered steps and a checklist of outcomes |
| `MAT-D18` | warning | A lab guide declares its duration |
| `MAT-D19` | warning | An ER diagram states each relationship's cardinality in words |
| `MAT-D20` | warning | A diagram takes its colours from the theme |
| `MAT-D21` | error | The document declares its kind, and the kind matches its filename |
| `MAT-D22` | error | The document uses the theme and no inline styling |
| `MAT-D23` | error | The HTML is well formed |
| `MAT-D24` | warning | Every image says what it shows |
| `MAT-D25` | error | Every review question carries its answer |
| `MAT-D26` | warning | Every objective is tested by a review question |
| `MAT-D27` | warning | A topic explains before it shows |
| `MAT-D29` | error | The parts a document must carry are present, in order |
| `MAT-D30` | warning | Every lab step says what the trainee should see |
| `MAT-D31` | error | Every objective item cites the objective code it serves |
| `MAT-D32` | error | A module has one lecture note |

### `MAT-D01` — The filename follows the module's naming convention

The index orders the module's decks; the lecture note is one file per module, named for its subject like its labs. A file outside the pattern sorts unpredictably, is never linked from the note's module map, and its kind cannot be told.

### `MAT-D02` — Indexes are unique within a folder

Two decks claiming the same position give the module two orders.

### `MAT-D06` — The first section states what a learner will be able to do

A document that opens with content has never said what it is for, and nothing downstream can map it to an objective.

### `MAT-D08` — A lecture note ends with review questions and somewhere to go next

Without them the note stops rather than closing, and a trainee revising for an exam or an interview has no way to test what they remember.

### `MAT-D09` — The review questions are enough for the module

At least two per topic, and never fewer than five: a handful of questions over a whole module samples a fraction of it, and the theory exam and the interviewer will not stop there.

### `MAT-D10` — Every code block declares a language

A block without `language-…` loses highlighting, and the convention is what lets `language-text` mark the blocks that are output rather than code.

### `MAT-D11` — Code languages come from the known set

An unrecognised tag is usually a typo; advisory because a module may legitimately introduce a new language.

### `MAT-D12` — Relative links resolve to a file that exists

A page pointing at a sibling that was renamed or never written sends the reader nowhere, and nothing reports it at render time.

### `MAT-D13` — Link anchors resolve to an id in the target

The module map, the syllabus map and the labs link into the lecture note's topics; renaming an id breaks them silently.

### `MAT-D16` — The text is in the language the document declares

`<html lang>` is what the theme, the exporters and the viewer follow for the words they write — a slide's default title, an answer's label, a PDF's session line. A module written in Vietnamese declares `vi`; a translation of an English original is a separate file ending `_vn`, so the original stays the thing every other document links to.

### `MAT-D17` — A lab guide has ordered steps and a checklist of outcomes

A lab without steps is an assignment brief, and one without an acceptance list leaves a learner unable to tell when they are done.

### `MAT-D18` — A lab guide declares its duration

The session plan allots it a number of minutes; a lab that never states one cannot be checked against that.

### `MAT-D19` — An ER diagram states each relationship's cardinality in words

Crow's-foot marks (`||--o{`) are read correctly only by someone who already knows the notation, which is what the diagram is teaching. A label beginning `1-1`, `1-n` or `n-n` says it plainly.

### `MAT-D20` — A diagram takes its colours from the theme

The material is read in light and dark mode. A colour fixed in the diagram is right in one and unreadable in the other, and it no longer matches the module's other diagrams.

### `MAT-D21` — The document declares its kind, and the kind matches its filename

`<meta name="fsa:kind">` is how the viewer, the exporter and `coverage` tell a deck from a note without guessing; a filename and a declaration that disagree mean one of them was copied from another file.

### `MAT-D22` — The document uses the theme and no inline styling

Every page links `_theme/fsa.css` and nothing else decides how it looks: no `style` attribute, no `<style>` element, no `<font>`. A one-off colour or size is how a module ends up with as many formats as authors, and it breaks dark mode and the exporters, which read the theme rather than the page.

### `MAT-D23` — The HTML is well formed

An unclosed element swallows whatever follows it — a slide into the next one, a section into the review questions — and a browser hides that by guessing, so the page looks right while the checker and exporter read something else.

### `MAT-D24` — Every image says what it shows

`alt` text is what a screen reader reads, what the exporter writes when an image cannot be placed, and what a trainee sees when it fails to load.

### `MAT-D25` — Every review question carries its answer

A trainee revising alone cannot tell a right answer from a wrong one without a model to compare against. The answer sits in `<details>`, so it is there when wanted and hidden until the trainee has answered.

### `MAT-D26` — Every objective is tested by a review question

An objective no question asks about is one a trainee can revise the module without ever checking; `data-objective` on each question makes the gap countable.

### `MAT-D27` — A topic explains before it shows

Code with no sentence in front of it asks the trainee to reverse-engineer the point. The idea comes first, in prose; the example illustrates it.

### `MAT-D29` — The parts a document must carry are present, in order

Each kind has a fixed shape — the objectives first, the summary before the review questions — so a trainee finds the same thing in the same place in every module, and the checker can find it too.

### `MAT-D30` — Every lab step says what the trainee should see

A step without an expected result leaves the trainee unable to tell whether it worked until three steps later, when it is hard to say which one went wrong.

### `MAT-D31` — Every objective item cites the objective code it serves

`data-objective` on each objectives item is what `coverage`, the summary and the review questions are compared against; an item without one is an objective nothing can trace.

### `MAT-D32` — A module has one lecture note

The note is the module in one place: the way through it, its theory and the map from the syllabus, the file a trainee revises from. A second one splits it, and a note per session — what this replaced — leaves the trainee to stitch the module together before an exam.


## Rules — a slide deck

Applied to a deck, against the FSA template.

| Rule | Severity | Checks |
|---|---|---|
| `MAT-S01` | error | The deck follows the template's order |
| `MAT-S02` | error | Every slide uses a template layout, and only that layout's slots |
| `MAT-S03` | error | A layout's required slots are filled |
| `MAT-S04` | error | The objectives slide states the session's objectives |
| `MAT-S05` | error | The summary answers the objectives |
| `MAT-S06` | warning | Every teaching slide has speaker notes |
| `MAT-S07` | warning | Every section has a check slide with its answer |
| `MAT-S08` | warning | A slot stays within its layout's limits |
| `MAT-S09` | warning | The number of slides fits the session's minutes |
| `MAT-S10` | warning | A title or short text keeps close to the template's size |
| `MAT-S11` | warning | A content slide fills its space |
| `MAT-S12` | warning | Every section shows something, not only tells |
| `MAT-S13` | warning | A picture is drawn for its slot |

### `MAT-S01` — The deck follows the template's order

Cover, an optional table of contents, Lesson Objectives — mandatory in the template — then each section opened by its section cover, then Lesson Summary and the closing slide. Trainees learn the rhythm once and every deck in the module then reads the same way.

### `MAT-S02` — Every slide uses a template layout, and only that layout's slots

A slot is a placeholder in the real template; content outside one has nowhere to go when the deck is exported to PowerPoint, and an unknown layout has no background, no geometry and no placeholder at all.

### `MAT-S03` — A layout's required slots are filled

A content slide with no title, or a cover with no lesson name, exports as the template's grey prompt text.

### `MAT-S04` — The objectives slide states the session's objectives

Each item carries `data-objective`, and together they cover every code in `fsa:objectives` — the codes the session plan says this lesson serves.

### `MAT-S05` — The summary answers the objectives

The template asks for the main points compared to the lesson objectives. Each summary item carries the `data-objective` it closes, and every objective is closed.

### `MAT-S06` — Every teaching slide has speaker notes

Notes are what the trainer says over the slide — the explanation the slide compresses. Without them the deck can be presented only by its author, and it cannot later become a recorded lesson.

### `MAT-S07` — Every section has a check slide with its answer

A question after each section — `data-role="check"`, the answer in `<details>` — makes trainees retrieve what they just saw, which is what fixes it; a deck that only presents is listened to and forgotten.

### `MAT-S08` — A slot stays within its layout's limits

Each layout sets how many items, words or lines of code fit at the template's type size. Past that the text shrinks or spills, and a slide read from the back of a room stops being readable.

### `MAT-S09` — The number of slides fits the session's minutes

Derived from `fsa:minutes` and `--minutes-per-slide`. Far too many slides for the time is a session that will be rushed or cut; far too few is one carried by the trainer's memory.

### `MAT-S10` — A title or short text keeps close to the template's size

A slot's text shrinks to fit, but past a point (`--min-fit`, 70% by default) the deck's titles stop being one size: one slide's at 36pt, the next at 22pt. The fix is fewer words, not a smaller box.

### `MAT-S11` — A content slide fills its space

Measured as `export pdf` lays the slide out (`--min-fill`, 60% by default): three bullets on a white slide leave its lower half blank, and a room reads a blank half as a slide with nothing to say. Show what the words describe — the picture, diagram, table or code — pick a layout with fewer, larger parts, or merge the slide with the next.

### `MAT-S12` — Every section shows something, not only tells

A section of bullets is heard and forgotten; a diagram, a screenshot, a table of real rows or code beside its output is what a trainee remembers and comes back to. Each section carries at least one.

### `MAT-S13` — A picture is drawn for its slot

A picture scaled to fit a slot of another shape leaves the slot part empty, and the text in it shrinks with it: a 3:2 drawing in `content-picture`'s near-square slot is cut to two thirds, its 15-unit labels to 7pt. Draw at the slot's shape (`references/material/layouts.md` gives each box) so the picture fills 60% or more of it and its smallest text is 12pt on the slide.


## Rules — exporting

Applied by `export`, `handout` and `verify --export`: what a .pptx or .pdf cannot carry, and what reaches trainees.

| Rule | Severity | Checks |
|---|---|---|
| `MAT-X01` | warning | A diagram exported to a file has a rendered image |
| `MAT-X02` | warning | Every slot's content fits its placeholder |
| `MAT-X03` | warning | Every image an export embeds is a PNG, JPEG, GIF or SVG inside the module |
| `MAT-X04` | warning | An SVG uses only what the exporters can draw |
| `MAT-X05` | warning | A line of code fits the printed page |
| `MAT-X06` | error | Every document handed to trainees has its current PDF |
| `MAT-X07` | warning | The hand-out holds only what a trainee is given |

### `MAT-X01` — A diagram exported to a file has a rendered image

Mermaid is drawn by the browser. PowerPoint and the PDF writer cannot run it, so a diagram needs an `<img>` of itself inside its `<figure>`, or it is exported as its source text.

### `MAT-X02` — Every slot's content fits its placeholder

Found while drawing the PDF: text that does not fit even after shrinking to the smallest readable size is cut, so the slide says less than its author wrote.

### `MAT-X03` — Every image an export embeds is a PNG, JPEG, GIF or SVG inside the module

PowerPoint and the PDF writer place raster images: an SVG is drawn to a PNG for them, and anything else is skipped. And an export embeds files from the module's own folder: a `src` reaching out with `../` would put an unrelated file into a deck handed to a class.

### `MAT-X04` — An SVG uses only what the exporters can draw

The export draws an SVG with svglib, which has no markers, filters, masks, patterns, text paths or HTML inside the SVG. Each would vanish from the slide handed out while the browser still shows it: draw an arrowhead as a polygon, and leave out the shadow.

### `MAT-X05` — A line of code fits the printed page

The PDF writer neither wraps nor shrinks a code block: a line past the page's width (about 95 characters, fewer inside a list) is cut at the margin while everything still passes. Break the line where the language allows.

### `MAT-X06` — Every document handed to trainees has its current PDF

`material handout` copies the decks', the lecture note's and the labs' PDFs. A document with no PDF, or one older than its HTML, would hand trainees nothing or last week's version, so it is refused until it is exported again.

### `MAT-X07` — The hand-out holds only what a trainee is given

Trainees get the slides, the lecture note and the labs as PDFs; a deck's `.pptx` is the trainer's, to present from. Anything else in the hand-out folder would be sent with it.


## Rules — material against the session plan

Applied by `coverage`, comparing a folder with the plan that asks for it.

| Rule | Severity | Checks |
|---|---|---|
| `MAT-C01` | error | Every material the session plan names exists |
| `MAT-C02` | warning | Every material in the folder is used by a session |
| `MAT-C03` | warning | A material's objective codes match the session that uses it |
| `MAT-C04` | warning | Every objective code cited is defined in the syllabus |

### `MAT-C01` — Every material the session plan names exists

The plan is a promise about what will be taught. A named file that does not exist is a session with nothing to deliver.

### `MAT-C02` — Every material in the folder is used by a session

A material nobody schedules is either unfinished or forgotten.

### `MAT-C03` — A material's objective codes match the session that uses it

The plan says which objectives a session serves; material claiming different ones is teaching to a different goal.

### `MAT-C04` — Every objective code cited is defined in the syllabus

A code the syllabus does not list is a typo or a missing objective.
