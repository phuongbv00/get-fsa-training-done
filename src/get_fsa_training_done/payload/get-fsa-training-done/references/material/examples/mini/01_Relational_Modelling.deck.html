Read the three outcomes aloud and tell the room that every example today uses one domain, a small library catalogue, so the pieces build on each other. By the end of the hour they will have the schema they implement in the lab that follows.

Entities and relationships

What the domain talks about

Entities are nouns with facts

  • Read the description and underline the nouns
  • A noun with its own facts is an entity: book, author, loan
  • A verb between two entities is a relationship
    • an author writes a book, a member borrows a book
  • Name entities in the singular
Put the catalogue description on screen and underline the nouns together. Point out that "title" is a noun but not an entity: it has no facts of its own, it is a fact about a book. That distinction is the whole skill on this slide.

The catalogue, drawn

Walk the diagram left to right. Read each label aloud, cardinality first: one author writes many books, one book is lent many times. Ask why book and author need the table in the middle before moving on; the answer comes back under normalization.

Which of these is an entity?

A member borrows a book on a date and returns it by a due date.

  • member
  • date
  • due date
Answer

Member: it has facts of its own. The dates are facts about a loan.

Give the room thirty seconds to decide before revealing. If someone says the loan is missing from the list, they are right: the verb "borrows" hides an entity, which is the point to land before the next section.

Keys

How a row is found again

Three kinds of key

Every table has one primary key, chosen from its candidates

Candidate

Primary

Foreign

Any column set that identifies a row uniquely, such as isbn.

The candidate you choose to identify rows. It never changes.

A column that holds another table's primary key.

Use the book table for all three: id and isbn are both candidates, id is the primary key, and book_author.book_id is a foreign key. Keep coming back to "never changes" because it decides the next slide.

Prefer a surrogate key

CREATE TABLE book (
  isbn  CHAR(13) PRIMARY KEY,
  title TEXT NOT NULL
);

An ISBN can be reissued.

CREATE TABLE book (
  id   BIGINT PRIMARY KEY,
  isbn CHAR(13) NOT NULL UNIQUE,
  title TEXT NOT NULL
);

The ISBN stays unique, but nothing points at it.

Ask what happens to every loan row when a publisher reissues an ISBN in the left version. Then show that the right version keeps the uniqueness guarantee without making the ISBN something other tables depend on.

Is an email a good primary key?

A member table identifies members by their email address.

Answer

No. Emails change. Keep it UNIQUE and add a surrogate id.

This is the same question as the ISBN with a more familiar value. Let two or three people answer before revealing, and ask each one what would break when a member changes their address.

Normalization

Each fact stored once

Three normal forms, one rule each

1NF

One value per cell: no lists packed into a column.

2NF

Every column depends on the whole key, not part of it.

3NF

No column depends on another non-key column.

Say each rule as a question the trainee can ask of a table: is there a list in a cell, does this column need the whole key, does this column really describe another column. The worked example on the next slide applies the first one.

A list in a column breaks 1NF

CREATE TABLE book (
  id      BIGINT PRIMARY KEY,
  authors TEXT
);
CREATE TABLE book_author (
  book_id   BIGINT
    REFERENCES book(id),
  author_id BIGINT
    REFERENCES author(id),
  PRIMARY KEY (book_id,
               author_id)
);
Ask how to find every book by one author in the left version: string matching, and it breaks on the first comma in a name. The relationship gets its own table, which is the table in the middle of the diagram from the first section.

Which form does it break?

loan(id, book_id, book_title, due_date)

Answer

3NF: book_title depends on book_id, not on the loan.

Point at book_title and ask what it describes. Once someone says "the book", ask where that fact should live. That is third normal form in one sentence, and it is the last idea before the summary.
  • Entities are the nouns with facts of their own; relationships are the verbs between them
  • A primary key never changes, so prefer a surrogate and keep natural values unique
  • Normalize until each fact is stored once: no lists, no partial or indirect dependencies
